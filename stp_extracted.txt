Project Overview and Detailed Description1.1 Background ContextThe Kalimati Market Analytics System The Kalimati Market Analytics system is a crucial piece of technological intervention aimed at upgrading and simplifying the process of collecting and analysing agricultural and wholesale market data. Traditionally, large wholesale markets such as the Kalimati deal with a massive daily flow of price, volume and supply chain data, which tends to exist in pockets, often manually maintained and extremely challenging to access in an aggregate and real time manner. This absence of real-time integrated data management and analysis can be the bane for farmers, wholesalers, retailers and even economic planners aiming for intelligent decision making based on actual data.The Kalimati Market Analytics System was created to fill this essential business need, and comprises a fully functioning, production-grade, full-stack software application. The fundamental purpose of this application is to ingest unprocessed (raw, unstructured/semi-structured) market data, organize and transform it into an efficient and query-optimized relational data model, and extract key intelligence and forecasting via: 1. Retrospective trend analysis; 2. Prospective forecasting The system allows the business to lessen their market volatility impact, improve logistics within their supply chains and foster a holistic understanding of market behaviors.1.2 Architectural BreakdownTo test properly and find an efficient test plan for it becomes important to delineate the architecture behind the system. The application is based on latest technology, technologies that have been chosen in order to make the system scalable in nature and are split into three major layers:Data Engineering and Automated ETL Pipeline: The foundation the system is an automated ETL pipeline driven largely by the dataextractionpipeline.py module. This is the primary layer where the system communicates with various external sources (like govt websites, public market APIs, raw CSV drops etc.) to fetch the pricing information on a daily basis. The Transform part is the most crucial aspect of the process where the data is meticulously cleaned up, imputing for missing values, dropping as per explicit business logic, transforming data types, converting date formats to UTC, enforcing referential constraints and then loading it into the data warehouse.Backend REST API Services and Database: The core backend is built with the FineASTAPI, which is a new and efficient framework to build robust RESTful back ends based on the Python programming language. It was decided to use FastAPI for its native async support, abundant type hints using Pydantic and auto-generated interactive API docs (Swagger UI/ReDoc). Data store: PostgreSQL: An open source Object Relational Datastore that is robust, reliable and ACID compliant and is recognized for its strength; is able to handle large volumes of data. SQLAlchemy Object-Relational mapper is abstracting your complex SQL queries into maintainable objects and with the PostgreSQL database adapter psycopg2-binary, there's a link between the FastAPI app and the PostgreSQL database. The web backend also includes some additional powerful analytics tools, using the Pandas library, very efficient in the manipulation of in memory data, and Statsmodels, for the implementation of the Autoregressive Integrated Moving Average (ARIMA) models used to build a mathematical model of previous times series to predict future ones. Last but not least, APScheduler has background task management operations, such as running the daily ETL cron or recasting ARIMA predictions at night.Frontend Presentation Layer: User Interface A Single Page Application (SPA) built using React, with vite serving as the build tool which means rapid HMR during development, along with highly optimized production asset builds. Client-side routing between the analytical pages such as executive dashboard, historical data grids, interactive forecasts are handled by the React Router library. In order to visualize the extensive data sets, and the predictive ARIMA lines, Recharts is used to display interactive charts built with native React components that can display dense market data in a responsive manner for the user.1.3 System Objectives and Business Value	The main goal of the Software project is to provide much needed agricultural market intelligence in an open fashion, eliminating data collection costs through 100% automation of the data pipeline and through the delivery of predictive intelligence, to also eliminate errors in manual data entry. The central business value for all Stakeholders is found in the accuracy of the ARIMA forecasts the application uses, thus allowing Stakeholders to predict price changes, purchasing trends, etc., thereby enabling optimization of the ordering and margins for purchasing of stocks. The Software Test Plan (STP) therefore must cover in great detail not only the functioning of the application code but the accuracy of the ARIMA predictions and the 100% integrity of the background automated operations.2.Comprehensive Testing ObjectivesThe test efforts for Kalimati Market Analytics System are not only an exercise in finding bugs but a process to develop and assure stability of system, data consistency and accuracy of analytical reports. Testing objectives have been divided into technical, operational and strategic goals.2.1 Technical Testing ObjectivesAPI Contract Adherence and Validation: Each endpoint of the FastAPI application must be rigorously tested against the generated OpenAPI schema including all the input request payloads, query parameters, authentication headers, etc. And that the response bodies be precisely the one specified by their schemas as JSON objects. We should check the HTTP status codes during positive and broad negative test cases (i.e. 200 OK, 400 Bad Request, 404 Not Found, 401 Unauthorized, 500 Internal Server Error etc.).ETL Pipeline Resilience and Idempotency: These methods prevent our dataextractionpipeline.py from being susceptible to surprising input, a flaky network connection, external timeouts or a data source which has errors or unexpected formatting. Tests also have to test explicitly that our ETL is idempotent; meaning it might get run twice in a day due to an incorrectly set-up scheduler, and that does not write out two copy rows into the database or corrupt history.Database Integration and Structural Integrity: To confirm that the SQLAlchemy models are mapped properly to the PostgreSQL physical schema, strictly enforcing primary key and foreign key constraints, along with database triggers. The tests should also test simple query performance, as not to impede significantly upon system performance due to history data retreivals.Frontend Component Rendering and State Management: Verify the React component unmount and mount without leaks in memory, with clean-up methods for each one; handle the complex state of the app (loading, error flags and display of returned data). Recharts diagrams have to perfectly represent the JSON object from the API, in size and responsiveness.2.2 Analytical and Operational ObjectivesAlgorithmic Validation of ARIMA Models: Verify with data and statistical calculation The purpose is to mathematically verify that the system is performing Statsmodels’ implementation of the ARIMA model properly. By supplying the system with a known and managed time series data for the historical period, and comparing the forecasting outcome with the manually calculated or cross-checked benchmark data, we could confirm that it’s statistically sound and mathematically precise.Automation and Orchestration Verification: Verify the APScheduler config thoroughly so that cron jobs/ interval based jobs can be triggered right on time based on server time (UTC/Local) and its run result (success/failure/retry) logged appropriately in audit log.Error Handling and Graceful Degradation: The purpose of this check is to verify that when a backend service or third-party service becomes unavailable or throws a transient error, the user sees friendly non-technical error messages (not a blank screen/application crash) and the backend is properly logging detailed stack traces for developers, without leaking any sensitive infrastructure information or security vulnerabilities into the frontend.2.3 Strategic Quality ObjectivesRequirement Traceability: In order to provide 100% test coverage on the functional and non-functional requirements captured within the Software Requirements Specification (SRS). All tests are to trace back to a particular business rule, user story or feature requirement proving what was requested was built correctly.Defect Leakage Prevention: Identify and fix all high severity and critical defects with a high degree of thoroughness during the System Testing phase. The intention is to ensure that no data corruption bugs, security bugs, or critical application crash bugs make it to the UAT phase or, more critically, the live production.Establishment of Quality Baselines: Develop an all-encompassing, re-useable set of manual & automated test cases, along with a baseline metric of system quality to serve as the primary foundation for regression test execution as the system grows, new functionality is introduced, and architectural dependencies evolve.3. Detailed Test Scope and StrategySpecifying the test scope is important in order to allocate quality assurance resources efficiently, establishing a level of stakeholder satisfaction and ensuring that the testing group focuses on the areas of highest technical risk and business value. This section describes exactly which functionalities, architectural layers and non-functional capabilities this test cycle cover, as well as those areas that are not included, to prevent scope creep.3.1 In-Scope Testing ComponentsThis Software Test Plan is specifically applicable to the following architectural layers, modules, and test techniques:3.1.1 Backend REST APIs (FastAPI)All GET requests for historic market prices which implement filtering by custom date range and by distinct commodity type and proper pagination.All GET requests to the forecasted data validating the integration of API Layer and output from the ARIMA Model.Thorough testing of data validation rules established by Pydantic Models(using Boundary Value Analysis as example for validating correct date formatting as per ISO-8601 format, and price as the strictly positive integer greater than zero).3.1.2 Data Engineering (ETL Pipeline)End-to-end execution of the dataextractionpipeline.py script.Use Equivalence partitioning to test data transformation logic to test how nulls, stripped whitespace and data type conversion is handled prior to DB insert.Verify APScheduler cron trigger that schedules this pipeline each day.3.1.3 Analytical Forecasting EngineQuick and efficient PostgreSQL data loading using Pandas DataFrames integrated into your structural model.Execution of ARIMA model training functions. Generating forecasting arrays.Confirmation of mathematical correctness of forecast bounds(upper and lower confidence intervals) provided by the forecasting engine along with the median forecast.3.1.4 Frontend Web Application (React/Vite)Routing and Navigation: Ensure React Router configurations is validated so all nav links, breadcrumbs, and dynamic url parameters points to correct authenticated views.Visualizations and Interactivity: Perform thorough UI tests on Recharts components: data tooltips upon hovering, dynamic axis scaling (with very low to extremely high prices in different sets of data) and performance without UI freezing when dealing with large dataset.Cross-Browser Compatibility: Functional web testing between different versions like mozilla, google chrome etc.Responsive Web Design (RWD): Testing the UI across different resolutions and breakpoints like dekstop’s(1920x1080) or Tablet(1024x768)etc.3.1.5 Testing Methodologies to be ExecutedUnit Testing (White Box): Test individual Python functions (e.g., testing string sanitation functions) in isolation. Test individual React utility hooks in isolation.Integration Testing (Gray Box): Verify that the communication routes and data serialization format for separate micro-components work properly (between API-to-Database layer and ETL-to-Database layer).System Testing (Black Box / End-to-End): A fully mocking a user from user's perspective flow, down to, simulating all the things a user could do, triggering an update to the backend ( etl ), and making sure that everything appearing on the user's UI is a valid ETL update ( both data is validated as it is ingested & validated as it is forecasted ) - validating the whole flow from the user's PoV without any knowledge of any internal user code.Regression Testing: After any change (bug fix or small commit), a predetermined collection of critical test cases is run to see if the newly added code caused something to regress (break) in the system, or if it was a feature that was added and affected only the subset of cases tried.User Acceptance Testing (UAT): SRS workflows verified by Business analysts, Subject matter experts or proxies for business sensibility.	3.2 Out-of-Scope Testing ComponentsIn order to maximize QA resource coverage on the accuracy and correctness of the functions for this first Release 1.0, all the following topics are explicitly out of the testing scope and no effort shall be spent testing them for this cycle.Stress, Load, and Volume Performance Testing: Simulating hundreds or thousands of simultaneous users or flooding the ETL pipeline with multiple-gigabyte dumps to break point are to be pushed to a later version; the design for the current release assumes an internally exposed or partially external system with users expecting functionality over speed.Security Penetration Testing and Vulnerability Scanning: Detailed security auditing, Penetration testing (Ethical Hacking), SQL Injection Automated testing, Cross-Site Scripting (XSS) Payload testing and Denial of Service (DDoS) Prevention test cases are not part of this functional test plan. Only normal input sanitisation and basic authentication flow shall be tested.Disaster Recovery and High Availability (HA) Testing: The responsibility for the testing of Database failover systems, server redundancy and Horizontal Auto Scaling or Backup & Restore will remain with the DevOps and Infrastructure teams and as such will be out of scope of this functional STP.Third-Party Infrastructure Operations: The internal logic of the APIs we scrape from, reliability of uptime for these external dependencies or the performance of their backends are not in scope of testing. Similarly, we don’t test the core architecture of the PostgreSQL engine or the build compiler in Vite. We are solely testing how our application responds to expected answers, timeouts or errors from those external systems.Native Mobile Application Testing: No Testing required on native iOS (Swift) or Android (Kotlin) mobile apps as we are only delivering web-based responsive apps.4. This plan makes use of a RACI matrix, where teams or individuals are designated as Responsible, Accountable, Consulted or Informed for all communication points.4.1 Key Stakeholders and RACI RolesProject Sponsor / Academic Lecturer (Accountable/Informed): The main authority and client representation that requires executive summaries that synthesize and deliver to executive level: project completion; general quality health; strict rubric adherence; project timing completion.Test Manager / QA Lead (Responsible/Accountable): Manages the overall creation, maintenance and execution of this STP. They will schedule all test executions, control the execution of the test communication plan, be responsible for arbitrating all disputes over the level of severity for any identified bugs and will produce all of the formal test documentation reports.Development Team - Frontend & Backend Engineers (Consulted/Informed): Developers These guys design the system and fix all the bugs they receive from the QA team. They must get descriptive and extremely reproducible reports. They must be constantly involved in discussions about all technical restrictions and environmental configuration.QA Team / Test Engineers (Responsible): Those who are actively engaged in design of test scenarios, implementation of tests manually and through automation tools, diligent recording of defects into bug tracking system along with evidence like screenshots and logs.4.2 Communication Channels and Standardized ToolingTo avoid communication silos, lost emails, and to maintain a source of truth throughout the team, communication will be highly formalized and directed through these tool sets:Defect Tracking System (e.g., Jira, Trello, or GitHub Issues): This is the required “official” way of communicating all issues. All bugs should not be submitted via email, chat or text without a ticket. All tickets must be extremely detailed with an ID number, the exact steps to reproduce, the expected and actual results, details of the environment (browser, operating system, API route), as well as relevant screenshots or server logs.Instant Messaging (e.g., Microsoft Teams, Slack, Discord): Here are the "official" processes to be used to log any and all issues All issues of bugs should be logged via a ticket. For the official weekly progress reports, forwarding critical blocking issues for management attention, circulating meeting minutes, and presenting for the final milestone approval documentation.Shared Document Repository (e.g., Google Drive, Confluence, SharePoint): Repository for STP, Test Case, SRS, API Doc, Execution logs which is central, versioned to enable stakeholders access to most recent and approved builds.4.3 Reporting Cadence and Meeting StructureA regimented and consistent schedule of regularly occurring meetings and reports will be observed throughout the test execution phase for the purpose of maintaining and actively monitoring all activities for risks.4.3.1 Daily Stand-up Sync (15 Minutes)Frequency: Daily (mornings) during active test run phase.Participants: Test Manager, Test Engineers, Lead Developers.Agenda: This is a fast format and everyone goes around to answer 3 key questions: What has been tested? Any blockers?Purpose: On the fly syncing and freeing up QA activities for an uninterrupted work experience for the team to create a collaborative culture4.3.2 Comprehensive Weekly Status ReportFrequency: End of the business week.Method: A formal email message which has been sent out to all of the stakeholders identified which includes an attached summary document in PDF format.Content:Execution Progress Metrics: Total of all designed test cases, executed, passed, failed, deferred and blocked in Percentage.Defect Density and Metrics: The number of active defects reported, sorted only by their severity (Critical, High, Medium, Low), and their present life cycle state (New, In Progress, Ready for Retest, Closed).Risk Assessment: Point out any part of the app that shows an unusually high number of bugs or a project that’s being endangered by some sort of external factors.Next Steps: A simple sketch of planned tests for next week and allocation of resource(s).4.3.3 Defect Triage MeetingFrequency: Twice a week(or more Depending on defect volume)Participants: Test Manager, Development Lead, selected Test Engineers.Agenda: Work through all new defects logged in the bug tracker: analyse defect impact, prioritze in development as P1-P4, check it is actually a bug or a misunderstanding of requirements, and assign to developer for a sprint.4.3.4 Test Execution Summary and Final Sign-off ReportFrequency: once, performed when all required testing has been completed at the formal end.Content: This is a complete, final document describing all testing performed throughout the testing effort.
